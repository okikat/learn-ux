# 有料化ロードマップ（さわって学ぶUX）

> 本書はレポート（提案）です。アプリ本体のコードは変更していません。
> 数値・工数は個人開発・小規模前提の目安です。最終判断は税理士／利用規約等の一次情報でご確認ください。

---

## 0. 現状の要点（最重要）

| 項目 | 現状 |
| --- | --- |
| 技術構成 | 静的SPA（React 19 + Vite）。GitHub Pages 配信、HashRouter。**バックエンド・認証・決済なし** |
| 無料/有料の概念 | 無料20法則 ＋「認知バイアス・パック（PRO, `¥980`）」14本（`src/data/laws.tsx` の `biasPack` / `biases`） |
| **PRO の保護状況** | **実質ノーガード。** `allLaws = [...laws, ...biases]` を `LawPage` が解決し、`/laws/:slug` で PRO 14本の**全文＋デモが誰でも閲覧可能**。`LawDetail` は tier に関係なく全描画。`biasPack.price='¥980'` は**表示のみ**で課金強制はゼロ。全PROデータが公開JSバンドルに同梱。 |
| 集客ファネル | 無料20本が入口。修了ページ（`/complete`）から PRO へ導線あり |
| 隠れた資産 | `npm run build:standalone`（`vite-plugin-singlefile`）で**単一HTMLに固められる** → ダウンロード販売の素地あり |

> **結論：** 売る前に必ず「**公開ビルドから PRO を除外**」する必要があります（今は有料相当が無料公開状態）。
> 静的SPAは配信されたJSが全公開＝クライアント側だけの“鍵”は原理的に破られます。
> 本当に守るなら「公開バンドルにPRO本文を含めない＋サーバ検証」が前提です。

## 1. 大方針（3つの選択肢）

### Option A ── マーケット/ダウンロード販売（最小工数・バックエンド不要）
PROパック（または全部入り版）を、決済・配信・できれば**税**まで代行してくれるプラットフォームで売る。
- 配信形態：`build:standalone` の単一HTML、ライセンスキー、または各プラットフォーム上の有料コンテンツ。
- 候補：**Booth（pixiv）／Gumroad／note（有料記事・マガジン）／Zenn（有料本）／Lemon Squeezy／Paddle**。
- 長所：数日で開始可。MoR（後述）が**消費税・インボイスを代行**。コードはほぼ不要。
- 短所：再配布されうる（性善説）。手数料。アプリ内に統合されない。

### Option B ── 統合ペイウォール（堅牢・高工数）
アプリ内でログイン→購入→PRO解放。
- 構成：認証（Supabase / Firebase / Clerk）＋決済（Stripe Checkout、または Paddle/Lemon Squeezy を MoR として）＋**サーバレスのWebhookで権利付与**＋**PRO本文を公開バンドルから外して認証後にAPI取得**。
- ホスティング：GitHub Pages はサーバ処理不可 → **Vercel / Netlify / Cloudflare Pages** へ移設（関数/Edgeが使える）。
- 長所：本物のゲート。サブスク・購入復元・統合UX。
- 短所：数週間の実装＋継続保守。SPAの“公開バンドルにPROを載せない”制約を厳守する必要。

### Option C（推奨）── ハイブリッド：まず A、伸びたら B
無料Webアプリは**集客ファネルとして維持**。最初は Option A で**早期に収益**を出し、手応えが出たら Option B で体験を磨く。

## 2. 課金モデルと価格

- **買い切り（推奨） vs サブスク**：マイクロ学習コンテンツは買い切りが摩擦小・解約管理不要。`¥980`（既定）は妥当な出発点。
- **アップセル設計**：将来「○○パック」を追加し、束ね売り／段階価格に。無料20本→PRO→新パック、と階段を作る。
- **初回ローンチ施策**：先着・期間限定の割引（希少性・アンカリング＝このアプリで教えている法則を自分に適用）。

---

## 3. 決済・税（日本）

- **MoR（Merchant of Record）を使うと楽**：Paddle / Lemon Squeezy / Gumroad / Booth / note 等が**消費税・インボイス・請求書**を代行。個人開発者に有利。
- **Stripe 直**：手数料は安いが、**消費税・インボイス・特商法対応を自分で**負う。
- いずれも**領収書／購入明細**の提供を用意。

## 5. 技術タスク（“売れる状態”にする最小実装）

1. **公開ビルドから PRO を除外**（必須・最優先）
   - ビルドフラグ（例：`VITE_TIER=public`）で `biases` を公開ビルドに含めない／PROカードは「購入導線」だけ表示。
   - 公開サイト＝無料20本、買い手向け＝34本（または別配信）。
2. **有料版の用意**：`build:standalone` で全部入り単一HTML、またはダウンロード成果物を生成。
3. （Option B 採用時）認証＋entitlement＋WebhookでPRO解放、PRO本文はAPI遅延ロード、ホスティング移設。
4. 計測・OGP・SEO（第8節）。

## 7. 推奨ファーストステップ（最短ルート）

1. **Booth / Gumroad / note** で PRO パックを出品（MoRで税を代行）。
2. **公開サイトから PRO を除外**（無料20本を入口に）。
3. **特商法表記・プライバシー・規約**を用意（特商法は原型あり）。
4. 決済 or ダウンロードの導線を、修了ページ／PROセクションに差す。

> これで「バックエンドを作らずに」最短で収益化を開始できます。手応えを見て Option B へ。

---

## 8. 計測・集客（運用）

- **解析**：プライバシー配慮型（Plausible / Cloudflare Web Analytics）。現状トラッキングなし＝プライバシーは良好だが、ローンチには最小限の指標が要る。
- **OGP/シェア**：現状 `index.html` に OGP/Twitterカード/`og:image` なし → シェア時に映えない。整備推奨（※HashRouter＋サブパス配信のため、URLごとのOGPはSSG/プリレンダ無しでは出ない点に注意）。
- **SEO**：HashRouter は各法則がクロールされにくい。集客を本気でやるなら History ルーティング＋プリレンダ（または静的書き出し）を検討。
- **導線**：修了ページ（ピーク・エンド）からの購入導線は良い設計。無料体験の“気持ちよさ”を維持。
